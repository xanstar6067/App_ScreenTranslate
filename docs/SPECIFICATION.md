# Техническое задание

## Android Overlay Screen Translator

**Версия ТЗ:** 0.1
**Этап:** MVP / полуавтоматический ручной перевод экрана

---

# 1. Назначение приложения

Разработать Android-приложение для перевода текста, отображаемого другими приложениями и играми.

Приложение должно:

* работать поверх других приложений;
* по команде пользователя захватывать текущий экран;
* локально распознавать текст на изображении;
* группировать распознанный текст в логические блоки;
* отправлять в сервис перевода только текст, а не изображение;
* отображать результат непосредственно поверх исходных областей экрана;
* не препятствовать взаимодействию пользователя с приложением или игрой под переводом.

Первый этап предусматривает только ручной запуск перевода.

Автоматический потоковый перевод и режим S Pen не входят в MVP, но архитектура приложения должна позволять добавить их позже без полной переработки основных компонентов.

---

# 2. Основной принцип работы

Общая схема:

```text
Пользователь включает приложение
        ↓
Запускается MediaProjection
        ↓
Появляется плавающая кнопка
        ↓
Короткое нажатие
        ↓
Получение текущего кадра экрана
        ↓
Локальный OCR
        ↓
Формирование текстовых блоков
        ↓
Определение языка / языков
        ↓
Проверка локального кэша
        ↓
Google / Yandex Web Translator
        ↓
Получение перевода
        ↓
Отображение overlay-блоков
        ↓
Кнопка превращается в «Очистить»
```

Изображение экрана ни при каких штатных условиях не должно отправляться во внешние сервисы.

Во внешнюю сеть передаётся только распознанный текст.

Основная платформа:

# 4. Главное окно приложения

Главное окно должно содержать следующие основные элементы.

## 4.1. Состояние приложения

Главный переключатель:

**«Включить экранный переводчик»**

Состояния:

```text
Выключен
Включается
Активен
Ошибка
```

При включении приложение:

1. проверяет необходимые разрешения;
2. при необходимости предлагает их выдать;
3. запрашивает разрешение Android на захват экрана;
4. запускает foreground service;
5. создаёт overlay;
6. показывает плавающую кнопку.

При выключении:

* закрывается MediaProjection;
* удаляется плавающая кнопка;
* удаляются все блоки перевода;
* останавливается foreground service.

# 5. Языки

## 5.1. Язык перевода

Поле:

**«Переводить на»**

Значение по умолчанию:

**Русский**

Пользователь должен иметь возможность выбрать другой язык из списка поддерживаемых сервисом перевода языков.

Выбор сохраняется между запусками приложения.

---

## 5.2. Исходный язык

Поле:

**«Язык оригинала»**

Основные варианты:

```text
Авто / смешанный
Английский
Японский
Корейский
Другой...
```

Для MVP основными приоритетными языками распознавания являются:

* английский;
* японский;
* корейский.

Дополнительно архитектура OCR должна позволять добавить:

* китайский;
* языки латинской письменности;
* деванагари;
* другие поддерживаемые OCR языки.

# 6. Режим «Авто / смешанный»

Приложение должно поддерживать наличие нескольких языков на одном экране.

Например:

```text
START

ゲームを続ける

로그인

Player 01
```

Необходимо распознать все четыре блока независимо от используемой письменности.

Для MVP в режиме «Авто / смешанный» одновременно используются OCR-модели:

```text
Latin
Japanese
Korean
```

Результаты нескольких OCR-проходов объединяются.

Необходимо удалять дублирующиеся результаты по:

* координатам;
* степени пересечения bounding box;
* совпадению текста;
* близости распознанного содержимого.

Для каждого итогового блока определяется наиболее вероятный язык.

Если блок содержит смешанные языки, например:

```text
Mission スタート
```

его не следует искусственно разбивать только из-за смены письменности.

Такой блок может быть передан переводчику с исходным языком `auto`.

# 7. Явно заданный исходный язык

Выбор языка пользователем должен уменьшать объём OCR-обработки.

### Английский

Используется:

```text
Latin OCR
```

### Японский

Используются:

```text
Japanese OCR
Latin OCR
```

Latin необходимо оставить из-за частого присутствия в играх:

* имён;
* названий предметов;
* чисел;
* элементов UI.

### Корейский

Используются:

```text
Korean OCR
Latin OCR
```

# 8. OCR

OCR должен выполняться локально на устройстве.

Базовая технология:

**Google ML Kit Text Recognition v2**

Для MVP модели:

```text
Latin
Japanese
Korean
```

предпочтительно включить непосредственно в приложение.

Это позволяет:

* не отправлять изображения в Google;
* работать без сети на этапе OCR;
* избежать ожидания загрузки модели при первом использовании;
* обеспечить предсказуемую работу.

OCR должен возвращать минимум:

```text
текст;
bounding box;
строки;
элементы;
координаты.
```

---

# 9. Формирование текстовых блоков

Это одна из важных частей приложения.

Нельзя считать каждую OCR-строку отдельным предложением.

Например изображение:

```text
I never thought that
we would meet again
in this place.
```

не должно превращаться в три независимых запроса:

```text
"I never thought that"
"we would meet again"
"in this place."
```

Предпочтительный результат:

```text
"I never thought that we would meet again in this place."
```

---

# 10. Алгоритм группировки текста

Первичным объектом следует считать `TextBlock`, возвращённый OCR.

Если OCR правильно сформировал блок, его строки объединяются в один переводимый фрагмент.

Дополнительно необходимо реализовать собственный этап:

**Text Block Reconstructor**

Он должен анализировать:

* расстояние между строками;
* высоту строк;
* горизонтальное выравнивание;
* пересечение по X;
* относительное положение;
* направление текста;
* предполагаемый язык;
* знаки пунктуации;
* близость соседних OCR-блоков.

Пример:

```text
Line 1 ─────────────┐
Line 2 ─────────────┼─ Paragraph #1
Line 3 ─────────────┘


             Line A ─────┐
             Line B ─────┴─ Paragraph #2
```

---

# 11. Эвристика объединения строк

Строки могут объединяться в один логический блок, если выполняется большинство условий:

* находятся непосредственно друг под другом;
* имеют близкую высоту;
* имеют похожее горизонтальное положение;
* расстояние между ними не превышает заданный коэффициент от средней высоты строки;
* не существует большого визуального разрыва;
* не наблюдается очевидного перехода к другому элементу интерфейса.

Не следует объединять:

```text
New Game

Settings

Exit
```

даже если эти элементы расположены вертикально рядом.

Следует объединять:

```text
We have to leave
this place before
the sun rises.
```

---

# 12. Настройка объединения текста

Добавить настройку:

**«Объединение строк OCR»**

Варианты:

```text
Осторожное
Нормальное
Агрессивное
```

По умолчанию:

**Нормальное**

Это позволит позже подстраивать приложение под разные игры без изменения алгоритма.

---

# 13. Захват экрана

Использовать Android `MediaProjection API`.

При активации приложения пользователь подтверждает системный запрос Android на захват экрана.

После этого MediaProjection остаётся активным в течение всей текущей сессии переводчика.

Короткое нажатие на overlay-кнопку не должно каждый раз вызывать системный диалог Android.

Кадр необходимо получать через:

```text
MediaProjection
↓
VirtualDisplay
↓
ImageReader
↓
Image / Bitmap
```

Изображение используется только в оперативной памяти.

Сохранять screenshot в галерею или файловую систему не требуется.

Разрешение на доступ к пользовательским фотографиям и файлам приложению не требуется.

---

# 14. Плавающая кнопка

После активации приложения создаётся одна плавающая кнопка.

Кнопку пользователь может перетаскивать по экрану.

Её положение сохраняется.

---

# 15. Состояния плавающей кнопки

## READY

Обычное состояние.

Иконка:

```text
Перевести
```

Короткое нажатие:

**сделать снимок и выполнить перевод.**

Долгое нажатие:

**открыть главное окно / настройки приложения.**

---

## PROCESSING

После короткого нажатия кнопка переходит в состояние обработки.

Возможное отображение:

```text
анимация;
вращающийся индикатор;
изменённая иконка.
```

Повторное короткое нажатие во время активной обработки игнорируется.

---

## TRANSLATED

После появления переводов кнопка превращается в кнопку:

**«Очистить перевод»**

Короткое нажатие:

* удаляет все переводные overlay-блоки;
* возвращает кнопку в состояние READY.

Долгое нажатие:

* по-прежнему открывает настройки приложения.

---

## ERROR

При ошибке:

* отображается короткое уведомление;
* кнопка возвращается в READY.

Например:

```text
Не удалось распознать текст
Нет соединения
Google недоступен
Yandex недоступен
Захват экрана невозможен
```

---

# 16. Исключение собственной кнопки из OCR

Перед получением screenshot приложение должно временно скрыть собственную плавающую кнопку.

Последовательность:

```text
Нажатие
↓
кнопка скрывается
↓
ожидание следующего кадра MediaProjection
↓
получение screenshot
↓
кнопка появляется в состоянии PROCESSING
```

Таким образом OCR не должен распознавать интерфейс самого переводчика.

---

# 17. Overlay перевода

Для каждого итогового текстового блока создаётся визуальный блок перевода.

Пример:

```text
Исходный участок:

┌───────────────────────┐
│ Mission Complete      │
└───────────────────────┘


Overlay:

┌───────────────────────┐
│ Задание выполнено     │
└───────────────────────┘
```

Положение блока основывается на bounding box исходного текста.

---

# 18. Overlay не должен блокировать управление

Все блоки перевода должны быть полностью `tap-through`.

Они:

* не получают touch;
* не получают focus;
* не блокируют жесты;
* не блокируют кнопки игры;
* не мешают свайпам;
* не мешают управлению игрой.

Плавающая управляющая кнопка является исключением.

Поэтому необходимо использовать два независимых overlay-слоя:

```text
Control Overlay
    └─ плавающая кнопка
       принимает касания

Translation Overlay
    └─ переводные блоки
       полностью пропускают касания
```

---

# 19. Внешний вид блока перевода

По умолчанию использовать контрастный фон.

Режим:

**Автоматический контраст**

Приложение анализирует среднюю яркость области под текстом.

Если область светлая:

```text
тёмный фон
светлый текст
```

Если область тёмная:

```text
светлый фон
тёмный текст
```

Фон слегка непрозрачный, чтобы полностью или почти полностью скрывать оригинальный текст.

---

# 20. Размер переводного текста

Размер текста должен автоматически подбираться под bounding box.

Алгоритм должен:

1. взять исходный размер области;
2. попробовать разместить перевод;
3. уменьшать размер шрифта до допустимого минимума;
4. при необходимости увеличивать высоту overlay-блока.

Не требуется любой ценой удерживать перевод строго внутри исходной области.

Читаемость важнее абсолютно точного совпадения размера.

---

# 21. Пересекающиеся блоки

Если после перевода соседние overlay-блоки начинают пересекаться:

* попытаться уменьшить размер текста;
* затем объединить близкие блоки;
* либо немного сместить блок.

Необходимо избегать наложения одного перевода на другой.

---

# 22. Сервисы перевода

MVP должен поддерживать:

```text
Google
Yandex
```

Архитектура должна позволять добавление других сервисов.

Интерфейс:

```kotlin
interface TranslationProvider {
    suspend fun translate(
        blocks: List<TranslationRequest>
    ): List<TranslationResult>
}
```

Пример реализаций:

```text
GoogleWebTranslationProvider
YandexWebTranslationProvider
```

---

# 23. Google — механизм по принципу TWP

Не использовать Google Cloud Translation API.

Использовать механизм, аналогичный Translate Web Pages.

## 23.1. Получение авторизации

Приложение запрашивает JS-ресурс веб-переводчика Google.

Из содержимого выполняется поиск значения:

```text
x-goog-api-key
```

Полученный ключ сохраняется только временно.

Необходимо хранить:

```text
ключ;
время получения;
состояние последней попытки.
```

Ориентировочное обновление:

```text
при отсутствии ключа;
при ошибке авторизации;
периодически после истечения внутреннего TTL.
```

Не следует выполнять получение ключа перед каждым переводом.

---

# 24. Google — запрос перевода

Базовый механизм TWP использует endpoint вида:

```text
https://translate-pa.googleapis.com/v1/translateHtml
```

Метод:

```text
POST
```

Основной заголовок:

```text
X-goog-api-key: <полученный ключ>
```

Текстовые блоки допускается объединять в один запрос.

Для сохранения соответствия:

```text
OCR block 0
OCR block 1
OCR block 2
```

можно использовать HTML-разметку с индексами по принципу TWP:

```html
<pre>
<a i=0>First text</a>
<a i=1>Second text</a>
<a i=2>Third text</a>
</pre>
```

После получения ответа индексы восстанавливаются и перевод связывается с исходным bounding box.

---

# 25. Google — ограничения

Google Web Provider необходимо считать неофициальным и потенциально изменяемым.

Его реализация должна быть полностью изолирована от остального приложения.

При изменении endpoint или авторизации должно быть возможно исправить только:

```text
GoogleWebTranslationProvider
```

без изменения:

* OCR;
* overlay;
* MediaProjection;
* UI;
* кэша.

---

# 26. Yandex — механизм по принципу TWP

Не использовать платный Yandex Cloud Translation API.

Использовать механизм веб-виджета.

---

# 27. Получение Yandex SID

Выполняется запрос JavaScript веб-виджета Yandex Translate.

Из ответа извлекается:

```text
sid
```

SID используется в последующих запросах перевода.

Необходимо кэшировать:

```text
SID;
время получения.
```

Повторное получение выполняется:

* после истечения TTL;
* при ошибке;
* если сервис отвергает текущий SID.

---

# 28. Yandex — запрос перевода

Используется endpoint веб-виджета вида:

```text
https://translate.yandex.net/api/v1/tr.json/translate
```

с параметром:

```text
srv=tr-url-widget
```

Передаются:

```text
id=<SID>
format=html
lang=<source>-<target>
text=<текст>
```

При автоматическом исходном языке источник может быть опущен согласно механизму сервиса.

Несколько OCR-блоков допускается передавать одним запросом с сохранением их границ.

---

# 29. Fallback переводчиков

Добавить режим:

**Сервис перевода**

Варианты:

```text
Автоматически
Google
Yandex
```

По умолчанию:

**Автоматически**

Порядок по умолчанию:

```text
Google
↓ ошибка
Yandex
```

Если выбран конкретный сервис, автоматический переход к другому по умолчанию не выполняется.

Позже возможно добавить отдельную настройку fallback.

---

# 30. Ограничение размера запросов

Нельзя отправлять весь экран одним гигантским запросом.

Использовать пакетирование.

Ориентир для первой реализации:

```text
до ~800–1000 символов текста на один сетевой пакет
```

При превышении лимита блоки разбиваются на несколько запросов.

Один отдельный абзац следует по возможности сохранять целиком.

---

# 31. Локальный кэш перевода

Необходимо реализовать локальный кэш.

Технология:

```text
Room / SQLite
```

Ключ:

```text
provider
sourceLanguage
targetLanguage
normalizedOriginalText
```

Значение:

```text
translatedText
detectedLanguage
timestamp
```

Пример:

```text
en → ru
"Mission Complete"
"Задание выполнено"
```

Повторное появление такого текста не должно создавать новый сетевой запрос.

---

# 32. Нормализация кэша

Перед поиском:

* удалить лишние пробелы;
* привести переносы строк к нормальному виду;
* убрать OCR zero-width characters;
* сохранить регистр текста;
* не удалять значимую пунктуацию.

---

# 33. Сетевое поведение

Таймаут одного запроса:

```text
10–15 секунд
```

Нужно реализовать:

* отмену запросов;
* retry для временной сетевой ошибки;
* fallback;
* защиту от нескольких одинаковых запросов одновременно.

Если два блока содержат один и тот же текст, должен выполняться только один реальный запрос.

---

# 34. Разрешения Android

Главное окно приложения должно содержать раздел:

**«Разрешения и состояние»**

Для каждого разрешения отображается:

```text
✓ Разрешено
! Требуется
```

---

# 35. Overlay permission

Необходимо:

```text
SYSTEM_ALERT_WINDOW
```

Используется для:

```text
TYPE_APPLICATION_OVERLAY
```

Состояние проверяется через:

```text
Settings.canDrawOverlays()
```

Если разрешение отсутствует, пользователь может перейти в соответствующие системные настройки непосредственно из приложения.

---

# 36. MediaProjection

Разрешение на чтение экрана выдаётся через стандартный системный диалог Android:

```text
MediaProjectionManager.createScreenCaptureIntent()
```

Это не постоянное обычное runtime-permission.

В интерфейсе отображать состояние:

```text
Захват экрана: активен
Захват экрана: не активен
```

Кнопка:

```text
Разрешить захват экрана
```

запускает системный запрос.

---

# 37. Foreground Service

MediaProjection должен работать через foreground service типа:

```text
mediaProjection
```

В manifest должны быть объявлены:

```text
FOREGROUND_SERVICE
FOREGROUND_SERVICE_MEDIA_PROJECTION
```

Service:

```text
android:foregroundServiceType="mediaProjection"
```

Во время работы приложения отображается стандартное системное foreground-уведомление.

Например:

```text
Экранный переводчик активен
Нажмите, чтобы открыть приложение
```

---

# 38. Notification permission

На поддерживаемых версиях Android приложение должно проверять разрешение уведомлений.

Если оно отсутствует, предложить его выдать.

Отказ пользователя не должен приводить к аварийному завершению приложения.

---

# 39. INTERNET

В manifest:

```text
android.permission.INTERNET
```

Разрешение выдаётся автоматически системой и не требует отдельного диалога.

---

# 40. Не требуемые разрешения

Приложению не нужны:

```text
камера;
микрофон;
контакты;
местоположение;
файлы;
галерея;
Accessibility Service;
root;
Shizuku.
```

Если в дальнейшем они не понадобятся для новой функции, их добавлять не следует.

# 48. Защищённый контент

Некоторые приложения используют системную защиту содержимого.

Если MediaProjection возвращает:

```text

пустой кадр;
недоступный кадр;
```

приложение должно корректно сообщить:

```text
Не удалось получить изображение экрана.

```

Не пытаться обходить системные механизмы защиты.

---

# 49. Состояние без текста

Если OCR не обнаружил текста:

```text
Текст на экране не найден
```

Кнопка возвращается в READY.

Пустой запрос переводчику не отправляется.

---

# 50. Приватность

Основное правило приложения:

**изображение экрана обрабатывается только локально.**

Во внешний сервис отправляется исключительно текст.

Screenshot:

* не сохраняется;
* не загружается;
* не логируется;
* удаляется из памяти после завершения OCR.

# 55. Требования к производительности

Ручной перевод не обязан быть real-time.

Однако интерфейс не должен зависать во время:

* OCR;
* сетевого запроса;
* построения overlay.

Все тяжёлые операции выполняются вне UI thread.

Желательная субъективная реакция:

* кнопка меняет состояние немедленно;
* OCR начинается без заметной задержки;
* уже готовые cache-переводы могут показываться раньше сетевых результатов.

---

# 56. Частичное отображение результатов

Если часть текста найдена в cache, а часть требует сети:

1. cached translation можно показать сразу;
2. остальные блоки показываются по мере получения результата.

Не требуется обязательно ждать завершения перевода всего экрана.

---

# 57. Обработка ошибок отдельных блоков

Ошибка одного текста не должна отменять весь screenshot.

Например:

```text
Block 1 → OK
Block 2 → ошибка
Block 3 → OK
```

Overlay должен показать перевод для 1 и 3.

Block 2 остаётся без overlay.

# 58. MVP — обязательные функции

Для первой рабочей версии обязательны:

* главное окно;
* включение/выключение сервиса;
* проверка разрешений;
* MediaProjection;
* одна плавающая кнопка;
* drag кнопки;
* короткое нажатие → screenshot;
* длинное → настройки;
* локальный OCR;
* English/Japanese/Korean;
* Auto/Mixed;
* формирование текстовых блоков;
* Google Web provider;
* Yandex Web provider;
* fallback Google → Yandex;
* overlay переводов;
* tap-through translation overlay;
* кнопка Reset;
* локальный cache;
* сохранение настроек.

# 59. Не входит в MVP

Пока не реализовывать:

```text
автоматический потоковый перевод;
определение изменений экрана;
S Pen Hover Translation;
ручное выделение области;
перевод отдельных областей по наведению;
OCR-видео в реальном времени;
перевод камеры;
историю screenshot;
облачное хранение;
аккаунты;
синхронизацию;
TTS.
```

# 60. Следующие этапы

После стабильной работы MVP архитектура должна позволить добавить:

### V2 — Auto Translation

```text
MediaProjection
↓
Frame Change Detector
↓
OCR только после значительного изменения
↓
Перевод только новых блоков
```

### V3 — S Pen

```text
S Pen hover
↓
координата стилуса
↓

```

При реализации текущего MVP эти будущие функции не должны требовать изменения API `OCRManager`, `TranslationManager` и модели `ScreenTextBlock`.

---

# 61. Критерии приёмки MVP

MVP считается функционально готовым, если выполняется следующий сценарий:

1. Пользователь запускает приложение.
2. Выбирает русский язык перевода.
3. Выбирает Auto/Mixed.
4. Нажимает «Включить».
5. Выдаёт необходимые разрешения.
6. Сворачивает приложение.
7. Видит плавающую кнопку поверх игры.
8. Нажимает её.
9. Приложение захватывает текущий кадр.
10. Изображение не отправляется в сеть.
11. OCR локально находит английский, японский или корейский текст.
12. Строки одного абзаца объединяются.
13. Текст переводится через Google или Yandex.
14. Перевод появляется примерно на месте оригинальных текстовых областей.
15. Переводные блоки не блокируют управление игрой.
16. Плавающая кнопка становится кнопкой очистки.
17. Пользователь нажимает её.
18. Все переводные блоки исчезают.
19. Кнопка снова готова выполнить перевод.
20. Долгое нажатие в любом рабочем состоянии открывает настройки приложения.
